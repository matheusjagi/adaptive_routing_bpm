# Adaptive Routing as Operational Insurance

Code and experiments for the paper *"Adaptive Routing as Operational Insurance: A
Training-Free Mechanism for Business-Process Decisions under Changing Costs"*
(M. O. Jagi, J. Montavão Filho, M. B. Costa), accepted at ICSOB 2026.

The repository implements a **cost-tracking, distance-vector routing policy** for a
business-process gateway. Each routable branch keeps a small table of estimated
cost-to-completion, updated as cases resolve (with the announcement lag of case
completion) and, optionally, from still-open cases (a censoring-aware *triggered update*).
The gateway then selects the cheapest branch, subject to a *hold-down* margin. No model is
trained and no process is re-mined; everything used at decision time was observable at
decision time.

## What is evaluated

- **Stage 1 — real data (tracking).** The event log of the BPI Challenge 2017 is
  replayed at the `A_Validating` activity. Its three successors (`O_Returned`,
  `A_Incomplete`, `W_Validate application`) are **not** interchangeable routing
  alternatives (see `exploration/check_branch_semantics.py` and
  `exploration/check_branch_independence.py`); they serve as three real, non-stationary,
  right-censored cost streams. Stage 1 measures how well the cost table tracks the
  currently cheapest stream (estimated regret against a proxy oracle), with announcement
  lag respected, end-of-log censoring corrected and hyperparameters frozen on a temporal
  split. The replay is open-loop: choices do not alter the recorded trajectories.
- **Stage 2 — semi-synthetic (selection).** A semi-synthetic environment with a *known true
  optimum* sweeps the drift rate to characterize *when* adaptive routing pays off.
  Produces the drift-pattern table and the phase diagram.

Here, *drift* means the change over time of each branch's completion cost caused by
evolving operational conditions (queues congesting and clearing), not *concept drift* in
the process-mining sense: the control-flow is fixed, only the costs move.

## Repository layout

```
src/                          core library
  config.py                   paths and every experiment constant (map 1:1 to the paper)
  load_log.py                 load / cache the BPIC2017 log
  decision_dataset.py         build the A_Validating decision dataset; censoring
  cost_table.py               sliding-window cost table T_t(b)
  triggered_updates.py        censoring-aware estimate from still-open cases
  policies.py                 static / periodic-recomputation / cost-tracking policies
  online_policies.py          streaming policy runner for Stage 2
  evaluation.py               proxy oracle + scoring (estimated regret, optimal rate)
  synthetic_drift.py          drift environment mu_b(t) for Stage 2
prepare_data.py               build the processed data from the raw log
run_final_analysis.py         Stage 1: tune -> freeze -> test, with paired statistical tests
run_synthetic_experiment.py   Stage 2: drift-pattern table + phase-diagram sweep
run_policies.py               quick single-run comparison of the policies
exploration/                  analysis probes, figure scripts and audit scripts
```

python -m venv venv && source venv/bin/activate

## Data

The experiments use the **BPI Challenge 2017** event log (van Dongen, 2017), a public
dataset: https://doi.org/10.4121/uuid:5f3067df-f10b-45da-b98b-86ae4c7a310b

Download `BPI_Challenge_2017.xes.gz` and place it in `data/raw/`. The raw log and the
derived files under `data/processed/` are **not** tracked by git; they are regenerated by
`prepare_data.py`.

## Reproducing the results

```bash
python prepare_data.py                        # processed log + decision dataset
python run_final_analysis.py                  # Stage 1 (Table 1, paired tests, monthly regret)
python run_synthetic_experiment.py            # Stage 2 (Table 2, phase diagram)
python exploration/plot_monthly_regret.py     # Fig. 3
python exploration/plot_synthetic.py          # Fig. 4
```

All experiment constants live in `src/config.py` and match the paper: 60-day warm-up,
30-day recomputation cadence, +/-14-day proxy-oracle window (evaluation only), temporal
tune/test split at 2016-07-01, triggered-update parameters (Delta = 14 days, beta = 1),
41-day end-of-log censoring buffer. Runs are deterministic.

## Audit scripts (camera-ready)

These scripts reproduce the additional numbers reported in the camera-ready version.
Run them from the repository root after `prepare_data.py`:

| Script | What it checks |
|---|---|
| `exploration/check_branch_semantics.py` | lifecycle semantics of the `A_Validating` successors |
| `exploration/check_branch_independence.py` | chi-square / Cramér's V of the successor vs. case attributes, resource and validation round |
| `exploration/audit_counts_and_claims.py` | evaluation counts, static branch, proxy-oracle variation, monthly decomposition |
| `exploration/check_block_inference.py` | week-level block bootstrap of regret differences |
| `exploration/check_tu_leakage.py` | re-selection of triggered-update parameters on the tuning period alone |
| `exploration/check_pathologies_period.py` | period and window variant of route flapping and lock-in |
| `exploration/check_monthly_choices.py` | monthly choices of the periodic baseline, cost tracking and proxy oracle |
| `exploration/probe_multihop_check.py` | shortest-path propagation vs. realized remaining time (multi-hop probe) |
